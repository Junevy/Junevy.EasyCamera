## 第 1 节：项目定位

`AGENTS.md` 第 1 节一句话定位：这是一个封装了海康、IRayple（华睿）工业相机 SDK 的类库，目标有三项——

- 便于在第三方项目开发中操作工业相机；
- 通过接口无缝更换相机硬件；
- 通过 Channel 管理相机帧。

三项目标直接决定了三条设计倾向：接口层要足够薄且稳定（换硬件不动消费方）；帧管理要以 Channel 有界队列为核心（背压可控、可丢帧统计）；SDK 差异必须被厂商适配层吸收。

## 第 2 节：三条注意事项

这是全仓库的技术红线，违反其中任何一条都会造成现场事故：

1. **非托管资源**——工业相机 SDK 大多底层由 C++ 实现，存在大量非托管资源（图像数据 `IntPtr` 等），开发时务必小心非托管资源泄露、忘记释放。
2. **少分配**——图像可能占用内存较大（5MB+），为性能考虑应尽量做到少分配图像与非托管资源。
3. **深拷贝**——Clone 图像时应尽量深拷贝，避免工业相机缓存队列爆满而丢失帧。

> [!danger]
> 第 3 条的动机是厂商 SDK 侧的缓冲池：帧缓冲来自 SDK 内部循环队列，若克隆只是借用指针，SDK 收不到"这一帧已经没人要"的信号，队列就会一直满、一直接不到新帧。所以"Clone 一份独立的"不是洁癖，是硬件约束。

> [!tip]
> 这三条在实现层被固化为：SDK 回调帧必须在回调内归还；发布给订阅者的帧必须是对 SDK 缓冲的独立克隆——每帧仅在相机回调中克隆一次，多订阅者通过引用计数浅共享同一克隆（订阅者为只读消费者）；克隆缓冲由最后一个归零的引用持有者物理释放。详见 [[并发与资源/帧所有权与内存]]。

## 第 3 节：协作纪律

`AGENTS.md` 第 3 节原文六条，均为强制要求：

| 序号 | 纪律 | 落点 |
| --- | --- | --- |
| 1 | 设计功能或 API 变更，必须检索 Skills 目录中当前项目的 Skill 是否需要更新 | `skills/using-junevy-easycamera/SKILL.md` |
| 2 | 对于不明确的功能，必须提问 | 与用户确认后再动手 |
| 3 | 对于可扩展的功能，必须询问是否扩展 | 例如新增能力是加进基础接口还是新开能力接口 |
| 4 | 如果有更好的实现方式或当前实现方式不符合设计规范、存在风险，必须提醒并询问，并检索是否有更好的方式，然后询问是否按照更优方式实现 | 审查报告的"设计问题与处置"表即产物 |
| 5 | 每次代码修改完毕后，必须摘要内容记录到根目录 `CHANGELOG.md` | 最新条目在最上，逆序 |
| 6 | 每次更新项目后，需要更新项目介绍（第 4 项，如不存在则补充）到 `AGENTS.md`，便于交接其他 Agent | `AGENTS.md` 第 4 节 |

配套的两条文档位置说明：

- 项目入口文档是根目录 `README.md`（现状 / 快速上手 / 推荐用法 / 链路状态 / 运行与安装前置条件）。
- 面向消费方 Agent 的包使用说明书在 `skills/using-junevy-easycamera/SKILL.md`，可复制到任意 Agent 运行时的技能目录使用；**修改公共 API 后必须同步更新该文件**。

> [!warning]
> 纪律 4 的实践形态就是 `docs/` 下的审查报告：先审查、先提问、把取舍写清楚，再实施。2026-10-05 的实施计划 `docs/superpowers/plans/2026-10-05-review-findings-fix.md` 开头有一张"待用户确认的决策点"表（D1–D5），正是纪律 3 与 4 的产物。

## 第 4 节：项目介绍

第 4 节是每轮更新都要刷新的活文档，当前（1.2.0）固化了以下要点。

**项目结构**：三个 SDK 风格 csproj 工程，**双目标 `net48 + net8.0`**——`Junevy.EasyCamera.Core`（公共抽象、服务/管理器/帧流契约及基础模型）、`Junevy.EasyCamera`（厂商适配与公共实现）、`Junevy.EasyCamera.Tests`（公共层、服务层与海康生命周期/并发回归测试，测试宿主固定 x64）。

**构建与环境**：厂商 SDK DLL 位于仓库根目录 `Libs/`（`MvCameraControl.Net.dll`、`MVSDK_Net.dll`），所有工程统一从该目录引用；**第三方**包版本由根目录 `Directory.Packages.props`（中央包管理）统一维护，**本库版本写在各 csproj 的 `<Version>`，`AssemblyVersion/FileVersion` 写在手写的 `Properties/AssemblyInfo.cs`，三者必须同步**；net48 通过条件引用补充 BCL 兼容包，net8.0 使用 `System.Drawing.Common`；`global.json` 固定 SDK 9.0.316。

**打包纪律**：厂商托管封装必须随 NuGet 包分发，用无条件 `Pack` 项 + `PackagePath="lib/net48;lib/net8.0"`，**禁止**写成 `"lib/"`（会被 NuGet 忽略），**禁止**按 `$(TargetFramework)` 分条件（外层构建时该变量为空）。厂商原生驱动（如 `MvCameraControl.dll`）**不在包内**，属消费方环境前置条件。`Tests/Packaging/PackageContentTests.cs` 是打包内容的回归守卫。

**厂商状态**：IRayple 标记 `[Obsolete("未开发完毕", true)]`，`ServiceCollectionExtensions` 不注册其服务，`EnableIRayple` 与 Basler 一致抛 `NotImplementedException`；代码保留，并已补齐 `operationGate`、回调排空、attach 幂等、`LastError`（`AGENTS.md` 的原话是"必须与海康遵守同一套并发纪律"）。**对照代码，这只是部分落地**：参数/命令路径仍在 `operationGate` 之外，生命周期仍是多个 `int` 标志位，见 [[厂商适配/IRayple现状]]。

**并发纪律（新增厂商必须遵守）**：一切原生访问经厂商相机的 `operationGate`（海康收敛为 `ExecuteGuarded`/`TryExecuteGuarded`/`ExecuteDispose`），唯一例外是 SDK 采集回调线程；生命周期用单一状态枚举（`CameraState`）而非并行布尔标志位，任何失败路径必须回滚；门面按 cameraKey 串行（`GetKeyLock`）；`CameraStream.operationLock` 只保护订阅者注册表；`SupportedOSPlatform("windows")` 必须写在 `Properties/PlatformCompatibility.cs` 而非 csproj `<AssemblyAttribute>`。

**公共契约要点**：厂商独有能力用能力接口表达（`ILinkStatusProbeProvider`/`IBufferConfigurable`/`INamedCameraInfo`），`ICameraProvider` 只保留枚举/创建/分发；**链路探测的回退信号**：门面持有的恒为 `AggregateCameraProvider`（自身实现 `ILinkStatusProbeProvider`）；无厂商具备能力时聚合器返回 `Unknown`，`CameraService.TryProbeByVendor` 把厂商返回的 `Unknown` 视为"无法判定"，回退侵入式 `ProbeByOpenClose`（1.1.2 起，`Unknown` 不再是终态；详见 [[公共契约/能力接口与扩展点]]）；`CameraLinkStatus` 五态且默认值必须是 `Unknown`；背压只提供 `DropOldest`/`RejectNewest`；`ICamera.StopGrab()` 返回 `CameraResult`，`ICamera.LastError` 是厂商诊断的唯一出口；取参用 `TryGetParam<T>`/`TryGetEnumParam`，泛型分发由 `ParameterReader` 统一，厂商只实现 `IParameterSource` 的 6 个原语；`ICameraManager.Remove` 返回 `CameraRemoveStatus`；非 DI 入口 `EasyCamera.Create(...)` 返回 `EasyCameraHost`。

**测试工程约定**：`EnableDefaultCompileItems=false` + 显式 `Compile` 清单，**新增测试文件必须手工加入 csproj**，否则不会被编译、更不会执行；验收应核对"仓库内 `[TestMethod]` 总数 == 执行数"；`PackageContentTests` 找不到 nupkg 时断言为 Inconclusive，不产生假失败。

**知识库（第 5 节）**：本库的 Obsidian 知识库位于仓库内 `Junevy.EasyCamera.Wiki/`（随本仓库提交），入口 `知识库首页.md`，正文在 `zh/content/<主题>/`。用普通文件工具按路径访问（Read/Grep/Glob、shell），**不要**依赖 filesystem MCP——`@modelcontextprotocol/server-filesystem` 在客户端支持 roots 时会把允许目录替换成当前工作目录，看似读了知识库实际读的是代码仓库。开发前按首页"按场景找笔记"读相关笔记，改并发/资源代码前必读 [[并发与资源/并发纪律]]，改动对照 [[Agent协作/文档同步清单与任务配方]]；公共 API/契约、并发纪律、打包规则、厂商适配或设计决策变化时，**同一会话内**更新对应笔记（优先改已有笔记，新增笔记挂进首页分类索引）并更新首页"版本与时效"；写完运行 `git -C <知识库路径> status --short` 与 `diff --stat` 汇报，**不自行提交**。消费方仓库（如 AutomationSystem）只读本库，发现的不一致由本仓库会话核实后修正。

> [!danger]
> 显式 `Compile` 清单是本仓库最隐蔽的坑。2026-10-06 发现 CHANGELOG 声称的"6 项探测测试"实际一次都没跑过——仓库实有 98 个 `[TestMethod]`，只执行了 92 个，而报告结论写的是"全量通过"。新增测试文件后不查 csproj，等于绿色地缺席。

## 验收命令与基线

```powershell
dotnet build .\Junevy.EasyCamera.sln -c Release -v:minimal --no-incremental
dotnet test .\Junevy.EasyCamera.Tests\Junevy.EasyCamera.Tests.csproj -c Release --logger "console;verbosity=minimal"
```

验收基线（2026-10-09，1.2.0 验收修正后）：全量重建 **0 错误 0 警告**；`net48` 与 `net8.0` **各 149/149 通过**，仓库 `[TestMethod]` 总数 149 = 执行数（1.1.0 时为 122/122，1.1.1 新增包内容守卫 2 项得 124，1.1.2 批次 A 新增 9 项得 133，1.2.0 掉线批次新增 16 项得 149，含验收修正新增 4 项）。注：旧版本文档中的 "130" 来自未合入 master 的 worktree 分支（`junevy/beautiful-rhodes-b9a236`），master 在 1.1.1 时实为 124。

> [!tip]
> `--no-incremental` 不是形式主义：CA1416 这类程序集级平台标注告警只在全量重建时暴露，2026-10-06 正是靠全量重建发现 20+ 条 CA1416，顺藤摸瓜查出 `GenerateAssemblyInfo=false` 让 `<AssemblyAttribute>` 静默失效。增量构建看不到。

## 版本纪律

当前 `Junevy.EasyCamera.csproj` 与 `Junevy.EasyCamera.Core.csproj` 的 `<Version>` 均为 `1.2.0`，两个类库各自的 `Properties/AssemblyInfo.cs` 中 `AssemblyVersion`/`FileVersion` 均为 `1.2.0.0`（`InternalsVisibleTo("Junevy.EasyCamera.Tests")` 在主库那份里，供无硬件单测访问测试 seam）。**四处必须同步**，并把 `SKILL.md` frontmatter `description` 里的版本提示（如 `v1.1.1+`）一并更新——该提示曾落后一个版本，2026-10-06 才补正。

**包版本必须递增**：NuGet 按 `id + version` 缓存，同版本重发不会被消费方采用。修复打包类问题务必升版本，并在升级说明里写明"清理缓存"。2026-10-06 的链路探测回退修复**未升版本**（行为只在此前不可达的回退路径上变化），因此"1.1.1"存在修复前后两种构建；若已发布过 1.1.1 再重发同版本，消费方需清缓存才会拿到修复，2026-10-08 批次 A 已按计划升到 **1.1.2**（行为修正，无 API 变更）；掉线批次升到 **1.2.0**（新增公共 API `ICameraService.CameraDisconnected`，自行实现 `ICameraService` 的代码需补成员）。1.1.1 的升级清单见 [[Agent协作/文档同步清单与任务配方]] 引用的 `SKILL.md` 末节。
