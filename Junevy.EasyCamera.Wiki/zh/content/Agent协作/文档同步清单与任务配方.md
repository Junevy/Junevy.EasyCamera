## 改动类型 → 必须同步的文件

| 改动类型 | 必须同步的文件 |
| --- | --- |
| 任何代码修改 | `CHANGELOG.md`（追加摘要条目） |
| 公共 API/契约、并发纪律、打包规则、厂商适配、设计决策变化 | 本知识库对应笔记 + 首页"版本与时效"（`AGENTS.md` 第 5 节，随 `CHANGELOG.md`/`AGENTS.md`/`SKILL.md` 同一会话完成） |
| 发版（升版本号） | 两个类库 csproj 的 `<Version>`、两份 `Properties/AssemblyInfo.cs`、`SKILL.md` frontmatter `description` 里的版本提示（含 `.zcode` 副本） |
| 项目结构/契约/构建约定变化 | `AGENTS.md` 第 4 节（项目介绍） |
| 公共 API 变化（新增/改名/签名/枚举值） | `skills/using-junevy-easycamera/SKILL.md`；若 `.zcode/skills/` 下有副本，需一并同步（两份应保持哈希一致） |
| 新增厂商/能力/配置项 | `README.md`（品牌状态表、快速上手）、`AGENTS.md` 第 4 节、`CHANGELOG.md`、`SKILL.md` |
| 打包规则或依赖变化 | `CHANGELOG.md`、`AGENTS.md` 构建约定、`docs/代码审查报告-*.md`（如属缺陷修复） |
| 新增测试文件 | `Junevy.EasyCamera.Tests.csproj` 的 `<Compile>` 清单（否则不会被编译） |
| 遇到"build/test 全绿但消费方失败"类缺陷 | 补端到端消费方验证；必要时新增包内容守卫测试 |

> [!warning]
> "新增厂商/能力/配置项"那一行要动四个文件（外加知识库回写），是漏改成本最高的一类：漏 `README.md` 消费方查不到品牌状态，漏 `AGENTS.md` 下一个 Agent 以为没有这个能力，漏 `SKILL.md` 消费方 Agent 会照旧接口写代码。1.0.1 → 1.1.0 的八条破坏性变更全部登记在 `SKILL.md` 的"从 1.0.x 升级到 1.1.0"清单里。

## 任务配方

每条配方含步骤 / 验证命令 / 易错点，可直接复制为 checklist。

### 配方 1：新增一个相机品牌

1. 在 `Junevy.EasyCamera/Vendors/<Brand>/` 建目录，实现 `ICameraSdkSystem`、`IVendorCameraProvider`，产出 `ICamera` / `IFrame` / `ICameraInfo` 实现。
2. **一切原生访问经该品牌相机的 `operationGate`**（参照海康 `ExecuteGuarded`/`TryExecuteGuarded`/`ExecuteDispose` 三个守卫模板），生命周期用单一状态枚举，失败路径必须回滚。
3. 厂商 DLL 放入根目录 `Libs/`，csproj 用 `HintPath` 引用；**并追加无条件 `Pack` 项**：`Pack="true" PackagePath="lib/net48;lib/net8.0"`。
4. 四处注册联动：`CameraOptions` 增 `Enable<Brand>` 开关；`ServiceCollectionExtensions.AddEasyCamera` 按开关调用新增的 `Register<Brand>()` 并把 SDK 工厂加入 `sdkSystemFactories`；`EasyCameraBuilder` 增 `Enable<Brand>()`（往 provider/sdk 工厂列表各加一项）。聚合入口 `AggregateCameraProvider` 无需改动，它按 `IVendorCameraProvider` 集合自动聚合。细则见 [[厂商适配/新增品牌指南]] 第 7 步。
5. 同步四份文档（见上表"新增厂商/能力/配置项"一行）+ 本知识库回写 + `PackageContentTests.cs` 增加该 DLL 的断言。

验证命令：

```powershell
dotnet build .\Junevy.EasyCamera.sln -c Release -v:minimal --no-incremental
dotnet test .\Junevy.EasyCamera.Tests\Junevy.EasyCamera.Tests.csproj -c Release --logger "console;verbosity=minimal"
```

易错点：忘记 `Pack` 项 → 消费方 `FileNotFoundException`（正是 1.1.1 修的缺陷）；忘记新增测试文件加入 csproj 的 `<Compile>` 清单；`Properties/PlatformCompatibility.cs` 未同步。

### 配方 2：给相机新增一项厂商独有能力

1. 先判断是"所有厂商都必须支持"还是"某厂商独有"。独有 → **新增能力接口**，不得往 `ICameraProvider`/`ICamera` 加成员。
2. 在 `Junevy.EasyCamera.Core/Abstractions/` 定义接口（如 `IBufferConfigurable`、`INamedCameraInfo`）。
3. `AggregateCameraProvider` 以能力探测方式分发；无厂商具备该能力时返回安全默认（如 `CameraLinkStatus.Unknown`）。
4. 旧代码路径上的公开成员改为能力接口的**显式实现**（参照 `HikCamera.SetBufferCount`、`HikCameraInfo.SetDefinedName`）。
5. 同步 `SKILL.md` 的 API 速查与升级清单、`AGENTS.md` 第 4 节、`README.md`。

易错点：net48 **不支持默认接口实现（DIM）**，写"接口默认成员"会导致 net48 编译失败，且错误信息（CS0535/CS0111）会把人引向"测试桩写错了"的错误方向——2026-10-06 的 `CameraServiceProbeTests` 就是这么编译不过的。改完公共 API 忘记同步 `SKILL.md`。

### 配方 3：新增一个参数类型

1. 在 `IParameterSource` 增加一个读取原语（当前 6 个，含 `double`）。
2. 在 `Junevy.EasyCamera.Core/Common/ParameterReader.cs` 增加泛型分发分支与失败语义。
3. 各厂商只需实现新原语，**不要**在 `GetParam<T>` 里加 `typeof` 分支（历史上每个厂商各写一遍 typeof 链，已被统一取代）。
4. 若涉及数值窄化，long→int 走受检转换，越界按失败处理，禁止静默回绕。
5. 更新 `SKILL.md` 的取参行与 `AGENTS.md` 第 4 节"取参"条目。

易错点：加 `typeof` 分支到具体厂商类 → 回到被去重的旧形态；用 `default(T)` 判断失败 → 必须用 `TryGetParam<T>`/`TryGetEnumParam` 区分"值恰为 default"与"取参失败"；窄化静默溢出。

### 配方 4：修复一个并发缺陷

1. **先写能复现的回归测试**，确认它在修复前失败。
2. 改实现。
3. **再验证一次：临时去掉修复，测试必须失败**（2026-10-06 对 `Close` 的 per-key 锁与打包规则都做过这一步）。
4. 核对 `[TestMethod]` 总数 == 执行数（排除"测试没被编译"的假绿）。
5. 同步 `CHANGELOG.md`、`AGENTS.md` 第 4 节并发纪律、`docs/代码审查报告-*.md` 的处置表。

易错点：新测试文件没加进 csproj（绿色地缺席）；只验证"加了修复测试通过"，没验证"去掉修复测试失败"——测试可能根本没测到点上；失败路径不回滚状态 → 静默丢帧。

### 配方 5：发布新版本

1. `Junevy.EasyCamera.csproj` 与 `Junevy.EasyCamera.Core.csproj` 的 `<Version>` 递增；两个类库各自的 `Properties/AssemblyInfo.cs` 的 `AssemblyVersion`/`FileVersion` 同步为四段式；`SKILL.md`（及 `.zcode` 副本）frontmatter `description` 里的版本提示同步（如 `v1.1.1+`）。主包 nuspec 依赖 Core 的**同版本**，两个包必须一起升。
2. Release 构建即产出 nupkg（两个类库都设了 `GeneratePackageOnBuild=true`）；也可显式 `dotnet pack`。
3. 校验包内容：两个 TFM 下都应含厂商托管封装（`PackageContentTests` 断言此点；无产物时为 Inconclusive）。
4. **端到端消费方验证**：仅引用真实产出的 nupkg（主包 + Core 包都放进临时 feed）、零手工拷贝 DLL，net8.0 与 net48 各跑一次 `Initialize()` + `EnumerateCameras()`，详见 [[构建与发布/消费方端到端验证]]。
5. 文档同步（见上表），并在 `SKILL.md` 写升级清单；回写本知识库首页"版本与时效"。

```powershell
dotnet build .\Junevy.EasyCamera.sln -c Release -v:minimal --no-incremental
dotnet test .\Junevy.EasyCamera.Tests\Junevy.EasyCamera.Tests.csproj -c Release --logger "console;verbosity=minimal"
dotnet pack .\Junevy.EasyCamera\Junevy.EasyCamera.csproj -c Release
```

易错点：**NuGet 按 `id + version` 缓存，同版本重发不会被消费方采用**——版本没递增则验证失真（本次验证过程中即被缓存误导过一次）；升级说明必须写"清理缓存"，或提示删 `%USERPROFILE%\.nuget\packages\junevy.easycamera*`，自定义 `RestorePackagesPath` 时删对应目录。

### 配方 6：给帧流增加一种背压策略

1. **先实测 `System.Threading.Channels` 的 `BoundedChannelFullMode` 真实语义**，不要凭名字推断。
2. 在 `IStreamOptions` / `StreamOptions.BackpressureMode` 增加枚举成员并写清取舍。
3. 更新 `CameraStream.Publish` 的淘汰/拒收分支，保证被淘汰的帧**立即释放**（引用计数归零即释放非托管缓冲）。
4. 确认 `FrameStreamStatistics.Dropped` 统计口径覆盖新模式。
5. 同步 `README.md`、`AGENTS.md` 第 4 节、`SKILL.md`。

> [!tip]
> 已知结论：实测 .NET 的 `BoundedChannelFullMode.DropNewest` 与 `DropOldest` 行为**完全一致**（都淘汰最旧帧），所以本库刻意不提供"丢新帧"模式——提供即名不副实。现有两个策略：`DropOldest`（默认，淘汰最旧保留最新）与 `RejectNewest`（队列满时拒收新帧、按序处理已入队帧，适合线阵测量/计数这类不能丢帧也不能乱序的场景）。

易错点：淘汰分支忘记释放帧（每帧 5MB+ 直接漏）；`Publish` 在 SDK 采集线程上持 `operationLock` 做重活（订阅/退订被慢速释放阻塞，用户回调可能死锁）；帧级重活必须在锁外，锁只保护订阅者注册表。

## 通用易错点

> [!danger]
> 打包规则的两个坑（已踩过，写在 csproj 注释里）：① `PackagePath="lib/"` 在包内已存在 `lib/<tfm>/` 时会被 NuGet **整体忽略**，消费方依旧拿不到，必须逐 TFM 写全；② 多目标项目打包走**外层构建**，此时 `$(TargetFramework)` 为空，按 TFM 分条件的 ItemGroup 恒不执行，用 `Condition="'$(TargetFramework)' == ..."` 分组会静默漏文件，必须无条件分组 + 分号多路径。

> [!warning]
> 另外三件事：`GenerateAssemblyInfo=false` 会连带跳过 csproj 的 `<AssemblyAttribute>` 项，所以 `SupportedOSPlatform("windows")` 必须写在 `Properties/PlatformCompatibility.cs`；"手工把 DLL 拷到 exe 旁边"对 .NET Core 无效（程序集解析走 `deps.json` 的 TPA 列表）；厂商**托管**封装随包分发与厂商**原生**驱动需装运行时/PATH 是两回事，排错时须先区分。
