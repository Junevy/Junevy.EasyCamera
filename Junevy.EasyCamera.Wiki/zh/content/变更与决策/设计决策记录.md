## ADR-01 帧所有权：每帧克隆一次

**背景**。每帧 5MB+，AGENTS.md 明确要求"Clone 图像时应尽量深拷贝"，同时又要求少分配。多订阅者场景下"每个订阅者一份深拷贝"在帧率乘以订阅者数后不可接受。

**决策**。SDK 采集回调内**只克隆一次**，得到对 SDK 缓冲的独立克隆帧；多订阅者通过引用计数**浅共享**同一克隆；克隆缓冲由**最后一个归零的引用持有者**物理释放。SDK 回调帧必须在回调内归还。订阅者是只读消费者，发布方不得修改帧数据。

**理由**。5MB×N 份深拷贝是不可接受的热路径分配；引用计数把成本压到"每帧一次克隆"，同时满足硬件侧的深拷贝要求。

**代价与边界**。约束是订阅者**只读**——需要修改像素的消费者必须自己再拷一份。释放责任落在"最后一个归零者"上，实现上依赖帧包装器内部的 `refLock` 短临界区（这个竞态窗口曾真实存在，见 [[变更与决策/审查与修复记录]]）。**不得把物理释放固定为发布者**，否则其余浅引用悬空。

## ADR-02 帧分发：Channels 有界队列 + 每订阅者 worker

**背景**。一个相机的帧要扇出到多个订阅者，各自消费速度不同，且 handler 可能抛异常。

**决策**。用 `System.Threading.Channels` 的**非阻塞有界队列**（容量由 `StreamCapacity` 控制），**每个订阅者一个 worker**；handler 慢只丢帧、绝不阻塞采集线程；被淘汰/拒收的帧由流立即释放。

**理由**。实现简单、订阅者之间故障隔离——一个 handler 抛异常只影响它自己那一路（worker 异常终止时自移除订阅者 `RemoveDeadSubscriber`）。

**代价与边界**。N 个订阅者 = N 个常驻 await 任务，每订阅者一条队列的内存开销随订阅者数线性增长。丢帧被淘汰时必须释放帧引用，否则直接漏 5MB。这条决策放弃了"共享分发线程"（无法做故障隔离与按订阅者背压）与 `IObservable`（本项目的按订阅者容量、背压、统计语义在 `IObservable` 里无对应表达）。

## ADR-03 背压只提供两种策略

**背景**。`BackpressureMode` 最初考虑提供三种：丢最旧、丢最新、拒收新帧。

**决策**。只提供 `DropOldest`（默认，淘汰最旧保留最新）与 `RejectNewest`（队列满时拒收新帧、按序处理已入队帧，适合线阵测量/计数这类不能丢帧也不能乱序的场景）。**刻意不提供"丢新帧"**。

**理由**。实测 `System.Threading.Channels` 的 `BoundedChannelFullMode.DropNewest` 与 `DropOldest` **行为完全一致**（都淘汰最旧帧）。提供该选项只会名不副实，误导消费方以为自己控制住了语义。

**代价与边界**。消费方无法要求"优先保最新且丢最新"——但实测该需求在 Channels 上不可表达。取舍记录在 `docs/代码审查报告-2026-10-06.md` 的设计问题处置表里。丢帧通过 `FrameStreamStatistics`（`Published`/`Delivered`/`Dropped`）可观测，此前完全静默，现场无法区分"采集慢"与"消费慢"。

## ADR-04 厂商独有能力用能力接口表达

**背景（历史教训）**。1.0.1 为支持链路探测，把 `ProbeLinkStatus` 直接塞进 `ICameraProvider`——抽象成员，无默认实现。

**决策**。厂商独有能力一律用独立接口表达：`ILinkStatusProbeProvider`（可达性探测）、`IBufferConfigurable`（采集缓冲配置）、`INamedCameraInfo`（本地改名）。`ICameraProvider` 只保留所有厂商都必须支持的枚举/创建/分发。旧路径上的公开成员改为能力接口的显式实现。

**理由**。把独有能力塞进基础接口意味着"每加一个能力就破坏所有实现者"，1.0.0 → 1.0.1 的一次破坏性变更就是这么来的。更关键的是**双目标下 net48 不支持默认接口实现（DIM）**，无法用"默认成员"兜底——测试桩必须全部实现，写测试的人误以为有默认实现，直接得到 CS0535/CS0111 编译错误。

**代价与边界**。门面要靠能力探测（`is`/`as`）分发，聚合层代码略长；消费方想用探测能力需要显式做能力判断。**加新能力时新增接口，而不是往 `ICamera` 加成员**。

## ADR-05 生命周期用单一状态枚举

**背景**。`HikCamera` 曾用 `isOpen`/`isGrabbing`/`closing`/`callbacksEnabled`/`disposed` 五个并行布尔标志位表达生命周期。

**决策**。改用单一 `CameraState` 枚举（`Closed`/`Open`/`Grabbing`/`Closing`/`Disposed`），`Publish` 判定退化为一次状态比较；`Connect`/`Close`/`StartGrab`/`StopGrab`/`Dispose` 与全部参数路径统一经 `ExecuteGuarded`/`TryExecuteGuarded`/`ExecuteDispose` 三个守卫收敛（互斥 + 异常翻译成 `CameraResult` + `LastError` 诊断）。任何失败路径（含原生异常）必须回滚到进入前的状态。

**理由**。布尔标志位的组合合法性与异常路径回滚全靠人工保证。真实故障：`Close` 的显式失败分支会回滚，`catch` 分支不会，相机永久停在"关闭中"，`IsConnected` 仍为 true 却一帧都不下发——**静默丢帧且无任何错误上报**。枚举从结构上排除非法组合。

**代价与边界**。新增生命周期状态要改枚举（当前只有五个，基本稳定）。守卫模板要求每个原生调用都写成一个方法，禁止绕过。唯一例外是 SDK 采集回调线程，它只读状态并归还缓冲区。

## ADR-06 CameraLinkStatus 以 Unknown 为默认值

**背景**。三态枚举 `Connected`/`Occupied`/`Idle` 中，`Connected = 0`。

**决策**。扩为五态且默认值必须是 `Unknown`：`Unknown=0`（未能判定）、`Connected=1`、`Idle=2`、`Occupied=3`（在线但被独占）、`Unreachable=4`（枚举不到/掉线）。禁止把任何"确定状态"排到 0。

**理由**。C# 的 `default` 是 0，未初始化/漏赋值的变量会谎报"已连接"。此外语义也错：厂商重新枚举不到设备被归入 `Occupied`，消费方的相机设置对话框会把"相机没插"显示成"被占用"。

**代价与边界**。**破坏性变更**：按数值判断状态的代码必须改为按枚举成员判断（1.0.x → 1.1.0 清单第 8 条）。探测语义约定：`info` 无效或序列号为空 → `Unknown`；厂商探测抛异常（如 SDK 未初始化）→ 静默降级为侵入式回退，不把异常抛给界面线程；枚举不到 → `Unreachable`；侵入式回退无法区分"被占用"与"设备不存在"，按"被占用"保守表达并在文档注明。自持判定（注册表扫描）必须先行于可达性查询，因为本进程独占持有的相机会令可达性查询返回 false。

**约定的兑现（2026-10-06 复审发现缺口，当日修复）**。上面"无探测能力 → 侵入式回退"的约定曾在生产组合下并未兑现：DI/Builder 注入的 `AggregateCameraProvider` 自身实现了 `ILinkStatusProbeProvider`，无厂商具备探测能力时返回 `Unknown`，`CameraService` 把它当最终结论，回退只在 provider 自身不是 `ILinkStatusProbeProvider` 或厂商探测抛异常时触发（海康具备能力，故未暴露）。**决策（选项 B）**：让聚合层把"无人能探测"与"厂商如实报告 `Unknown`"区分开，门面在前者回退；信号走 **internal** 的 `IProbeAvailability.CanProbe(info)`，不改 `ILinkStatusProbeProvider`/`ICameraProvider`（net48 无默认接口实现，AGENTS.md 禁止给既有公共接口加成员），也不按具体类型嗅探（与 2026-10-05 移除 `is CameraManager` 嗅探同一原则）。**边界**：能力厂商如实返回 `Unknown` 仍是终态、不回退；直接调用聚合层 `ProbeLinkStatus` 的外部调用方仍只看到 `Unknown`。机制见 [[公共契约/能力接口与扩展点]]，修复与反向验证见 [[变更与决策/审查与修复记录]]。

## ADR-07 厂商托管封装打进 NuGet 包

**背景**。消费方 Agent 报告"SDK 初始化持续报错、枚举不可用，怀疑 nupkg 未声明厂商依赖"。端到端复现属实：`Initialize()` 抛 `AggregateException: The type initializer for 'HikCameraSdkSystem' threw an exception`，`EnumerateCameras()` 抛 `FileNotFoundException('MvCameraControl.Net, Version=4.5.0.2')`，未捕获即崩溃。而本仓库 build/test 全绿。

**决策**。在 `Junevy.EasyCamera.csproj` 中加**无条件** `Pack` 项把 `Libs/` 里的两份厂商封装打进 `lib/net48;lib/net8.0`，保持 `Libs/` 单一来源。**不**采用"依赖 nuget.org 上的第三方转包"。

**理由**。根因是 `<Reference HintPath=..\Libs\... Private=true>` 只让本仓库输出目录拿到 DLL，`dotnet pack` 既不把文件引用放进包内、也不产生依赖声明。放弃第三方转包是因为版本对不上（本地 pin **4.5.0.2** vs nuget.org 上只有第三方未验证转包 1.1.0 / 4.4.1.x / 4.8.0.3）——依赖它等于引入供应链风险。

**代价与边界**。两个坑必须记住：① `PackagePath="lib/"` 在包内已存在 `lib/<tfm>/` 时会被 NuGet **整体忽略**，必须逐 TFM 写全；② 多目标项目打包走**外层构建**，`$(TargetFramework)` 为空，按 TFM 分条件的 ItemGroup 恒不执行，必须无条件分组 + 分号多路径。防复发靠 `Tests/Packaging/PackageContentTests.cs`（已验证移除打包规则即失败）。另需区分：厂商**原生**驱动 `MvCameraControl.dll` 不在包内，属消费方环境前置条件（MVS 运行时 + PATH 含 `Runtime\Win64_x64`）；"手工拷 DLL 到 exe 旁边"对 .NET Core 无效（解析走 `deps.json` 的 TPA 列表）。

## ADR-08 双目标 net48 + net8.0

**背景**。消费方存在存量 .NET Framework 宿主（Prism/WPF 现场）与新项目两类。

**决策**。三个工程全部双目标 `net48 + net8.0`，SDK 风格 csproj，`LangVersion 13`，测试宿主固定 x64，`global.json` 固定 SDK 9.0.316，net48 通过条件引用补充 BCL 兼容包。

**理由**。丢掉 net48 就等于把现场项目挡在门外，违背"便于在第三方项目开发中操作工业相机"的项目目标。

**代价与边界**。net48 需条件引用 BCL 兼容包（`Microsoft.Bcl.AsyncInterfaces`、`System.Threading.Channels`、`System.Threading.Tasks.Extensions` 等）；**net48 不支持默认接口实现**，这直接推高了 ADR-04 的代价——任何"加个默认成员"的想法在双目标下都不成立，必须走独立能力接口。另外厂商 SDK 为 AMD64 专用，AnyCPU/x86 会抛 `BadImageFormatException`。

## ADR-09 平台标注写在 PlatformCompatibility.cs

**背景**。csproj 里写了 `<AssemblyAttribute Include="SupportedOSPlatform">`，但两个类库都设了 `GenerateAssemblyInfo=false`（为使用手写 `Properties/AssemblyInfo.cs`）。

**决策**。`SupportedOSPlatform("windows")` 写在 `Properties/PlatformCompatibility.cs`（`#if NET8_0_OR_GREATER`），测试工程同样补齐；移除两个 csproj 中失效的 `<AssemblyAttribute>` 项。

**理由**。`GenerateAssemblyInfo=false` 会**连带跳过** csproj 的 `<AssemblyAttribute>` 项——平台标注实际从未生效。全量重建时冒出 20+ 条 CA1416 告警（增量构建看不到），"两个类库在 net8.0 下声明程序集级 `SupportedOSPlatform`"这一既有结论是不成立的。**静默失效**比没有更危险：文档、约定、代码三处都写着"已声明"，唯独实际没声明。

**代价与边界**。多了一个必须同步的文件；新增工程时别只在 csproj 里写平台标注。

## ADR-10 门面暂不按 ISP 拆分

**背景**。`ICameraService` 有 22 个成员（`SetParam` 的 4 个重载各计一次；`docs/代码审查报告-2026-10-06.md` 里写的"25 个"是误数），枚举/生命周期/参数/探测/帧流混在一个门面。ADR-04 的原则下它同样"过胖"。

**决策**。本轮**不拆分**。记录在 `docs/代码审查报告-2026-10-06.md` 的"设计问题与处置"表里（问题：万能门面；处置：本轮未拆分，拆分会再次破坏消费方；记入后续）。

**理由**。1.0.1 → 1.1.0 已经是八条破坏性变更，短期内再动消费方主干接口收益不抵成本。`IStreamOptions` 那种"注册了却无人消费"的抽象空洞已经修过一轮（构造函数改为依赖 `IStreamOptions`），门面拆分可以等下一次大版本。

**代价与边界**。消费方拿到的仍是宽接口，能力隔离性弱于厂商层。后续拆分时注意：`ICamera` 已经因为 ADR-05/ADR-04 加过成员，再拆会叠加破坏。
