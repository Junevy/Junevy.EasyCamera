## 2026-09-15 稳定性全链路审查

审查确认两条主线设计正确：**帧主线**（回调内 Clone → 归还 SDK 缓冲 → 独立克隆发布 → 订阅者消费/淘汰/取消释放）与**相机关闭主线**（解绑回调 → StopGrab → 等待在途回调 → Close，失败回滚经 `RestoreCallbackSubscription`）。修复的是健壮性与并发窗口：

| 编号 | 关键问题 | 根因 | 修复 | 回归保障 |
| --- | --- | --- | --- | --- |
| H1【高危】 | 订阅 worker 因 handler 异常终止后仍留在订阅字典，后续 `Publish` 持续向已死订阅者通道写帧 → Channel 内滞留 `capacity` 帧（每帧 5MB+ 非托管缓冲）永不释放，且订阅静默失效 | 调用方未提供 `whenException` 时 worker `throw;` 终止，但 `Channel` 未 Complete，写入照常成功 | worker 异常终止时自移除订阅者并释放资源（`RemoveDeadSubscriber`，仅移除同 Key 同实例）；`CameraStreamSuber` 增加 `Key` 属性 | `Junevy.EasyCamera.Tests/Abstractions/CameraStreamRegressionTests.cs` |
| H2【高危】 | `HikFrameWrapper` 无 GC 兜底，订阅方忘记 `Dispose` 即永久泄漏非托管缓冲 | 克隆帧仅靠 `Dispose()` 释放，异常路径/疏漏无兜底 | 增加终结器兜底；原生释放成功后 `GC.SuppressFinalize` | 同上 + `Junevy.EasyCamera.Tests/Vendors/HikVisionRegressionTests.cs` |
| H3【高危】 | `AddRef` 与流侧最终 `Dispose` 并发存在 use-after-free 窗口：`refCount==1` 时消费方读到 1，流侧递减到 0 并释放，消费方 CAS(1→2) 仍成功 | 引用计数无同步，靠时序 | 改为 `refLock` 短临界区，串行化 `AddRef` 与最后一次 `Dispose` | `HikVisionRegressionTests.cs` |
| M1 | `WaitForCallbacks` 用 `Monitor.Wait` 无超时，SDK 回调挂死将永久阻塞 `Close`/`Dispose` | 无超时设计 | 增加 5s 有限超时，超时记 `LastError` 并继续关闭 | `HikVisionRegressionTests.cs` |
| M2 | SDK 全局 `Initialize`/`Finalize` 只有一个静态 `isInitialized`，任一实例 `Release` 会 `Finalize` 整个 SDK，其他在用实例失效 | 无跨实例协调 | 改为静态引用计数，引用归零才 `Finalize`；初始化失败回退计数 | `Junevy.EasyCamera.Tests/Vendors/HikCameraSdkSystemTests.cs` |
| M3 | `StreamManager` 无 disposed 状态，`Dispose` 后 `GetOrCreateStream` 会重建一个永远无人释放的流 | 与 `CameraManager` 的 disposed 防护不对称 | 增加 disposed 防护，释放后 `GetOrCreateStream` 抛 `ObjectDisposedException` | `Junevy.EasyCamera.Tests/Common/StreamManagerTests.cs` |

> [!warning]
> M3 是**"已声明修复但代码缺失"的回归**：`CHANGELOG` 2026-09-15 声称"释放后 `GetOrCreateStream` 抛 `ObjectDisposedException`"，2026-10-05 审查发现实际只有 `GetStream` 有检查。这是文档与代码脱节的实例，也是纪律 5（CHANGELOG 必须如实记录）的反面教材。

维持现状的轻微项：`HikFrameWrapper.Stride = ImageSize/Height` 对含行填充的格式可能不准、`SetBufferCount` 无锁读 `device`（有 catch 兜底）、`Dispose` 中 `StopGrabCore` 失败仍继续 `device.Close()`（best-effort）——评估后认为改动风险大于收益。移除了 `HikCamera.callbacksDrained` 死代码（只 Set/Reset 从不 Wait），保留 `Monitor.PulseAll` 排空机制。

## 方法论教训

> [!danger]
> **测试"全绿"不等于功能被验证。** 2026-10-06 进入审查时的状态是：build 0 错误 0 警告、test 双目标 92/92 通过、报告结论写"全量通过"——但仓库实有 **98** 个 `[TestMethod]`，只执行了 **92** 个。缺的 6 个恰是新加的 `CameraServiceProbeTests`，原因只是它没被加进 csproj 的显式 `Compile` 清单。这 6 个"绿色地缺席"的测试里如果有一条能发现问题，这次审查的 P0 结论就会不同。此后约定：验收必须核对"仓库内 `[TestMethod]` 总数 == 执行数"。

> [!warning]
> 第二个教训：**单元测试天然测不到打包缺陷**。消费方崩溃时仓库全绿，因为缺失发生在 NuGet 打包环节而非代码逻辑。这类缺陷只能靠"直接校验打包产物"的守卫测试 + 端到端消费方验证来防。

> [!tip]
> 第三个教训：**修复必须做反向验证**。`Close` 的 per-key 锁与打包规则两项修复都做过"移除修复 → 测试必须失败"的验证，才能证明测试真的在测这个点。
