# 稳定性全链路审查报告（2026-09-15）

审查范围：`Junevy.EasyCamera.Core`（IFrame 契约）、`Junevy.EasyCamera`（HikVision 厂商适配、CameraStream/CameraStreamSuber、CameraManager/StreamManager/CameraService、SdkSystem）。
IRayple 分支为 `[Obsolete]` 未开发状态，不在本次审查范围。

## 一、高危（真实缺陷，建议修复）

### H1. 订阅者 worker 死亡后帧滞留 + 数据流静默失效
- 位置：`Common/CameraStream.cs`（`ConsumeAsync` + `Publish`）+ `Common/CameraStreamSuber.cs`
- 现象：当 `processFrame` 回调抛异常且调用方**未提供** `whenException` 时，worker 捕获后 `throw;` 终止。但该订阅者仍留在 `subscribers` 字典中，后续 `Publish` 会继续 `AddRef()` 并 `TryWrite` 成功（Channel 未 Complete）。
- 后果：
  1. Channel 内滞留 `capacity` 帧永远无人消费、无人 Dispose（DropOldest 只在满后丢弃新入队之外的旧帧，滞留帧恰好等于容量，每帧为独立克隆的 5MB+ 非托管缓冲）；
  2. 订阅静默失效，上层无任何感知，无自愈路径。
- 建议：worker 异常终止时自清理——从 `subscribers` 移除自身（经 `operationLock`），或 `CameraStream` 监控 `Subber` Task 完成状态做移除 + 可选异常通知。

### H2. HikFrameWrapper 缺少 GC 兜底，忘记 Dispose 即泄漏原生缓冲
- 位置：`Vendors/HikVision/HikFrameWrapper.cs`
- `IFrameOut`（克隆帧，独立非托管缓冲）由 wrapper 持有，仅靠 `Dispose()` 释放。若订阅方拿到 `IFrame` 后忘记 Dispose（异常路径、代码疏漏），该非托管内存**永久泄漏**，无 finalizer/SafeHandle 兜底。
- 建议：增加 finalizer（或 `~HikFrameWrapper` + `Dispose(bool)` 模式）作为最后防线，并在 IFrame 接口 XML 注释中明确"必须 Dispose"的所有权契约。

### H3. AddRef/Dispose 竞态存在 use-after-free 窗口
- 位置：`HikFrameWrapper.AddRef/Dispose`
- 场景：`refCount == 1` 时，消费方（如 handler 内）调用 `AddRef()` 与流侧最终 `Dispose()` 并发：消费方读到 `current=1`，流侧递减到 0 并释放原生帧，消费方 CAS(1→2) 仍成功 → 继续访问已释放的非托管内存。
- 说明：流内部路径（Publish 在 `operationLock` 内 AddRef）是安全的；风险仅在消费方于 handler 结束前后直接调用 `AddRef/Dispose` 时。
- 建议：明确契约——`AddRef` 必须在 handler 返回前完成引用转移；或将引用计数改为"Dispose 前先做 disposed 检查 + 加锁短临界区"的保守实现（帧操作非每帧热点路径时开销可接受）。

## 二、中等（健壮性/长期运行风险）

### M1. WaitForCallbacks 无超时，SDK 回调挂死将永久阻塞 Close/Dispose
- 位置：`HikCamera.WaitForCallbacks`（`Monitor.Wait` 无超时）
- 建议：加有限超时（如 5s），超时记录 `LastError` 并继续关闭。

### M2. HikCameraSdkSystem 全局 Initialize/Release 无引用计数
- 位置：`Vendors/HikVision/HikCameraSdkSystem.cs`（静态 `isInitialized/disposed`）
- 多个 CompositeCameraSdkSystem / 服务实例并存时，任一实例 `Release()` 会 `SDKSystem.Finalize()` 整个 SDK，导致其他在用实例失效；`Dispose` 只防自身重复，不防交叉。
- 建议：静态引用计数，归零才 Finalize。

### M3. StreamManager 无 disposed 状态
- `Dispose()`/`RemoveStream()` 之后调用 `GetOrCreateStream()` 会重新创建流并常驻字典，永远不会被释放；与 CameraManager 的 `disposed` 防护不对称。
- 建议：增加 disposed 标志，Dispose 后拒绝 GetOrCreate。

### M4. CameraService.cameraOpenLocks 只增不减
- 每个 cameraKey 永久保留一把锁对象。长期运行、动态上下相机（key 含序列号/时间戳）时缓慢增长。
- 建议：Close 时按引用计数移除，或接受现状（量级小）并在注释说明。

## 三、轻微（可维护性/一致性）

1. `HikCamera.callbacksDrained`（ManualResetEventSlim）与 `Monitor.PulseAll` 双机制并存，前者只 Set/Reset 从不 Wait，属死代码，建议二选一。
2. `CameraService.StopGrab` 使用服务级 `locker` 而 `StartGrab` 不锁，不对称且服务级锁粒度过大。
3. `IFrame.GetBitmap()` 的 Bitmap 所有权（调用方负责 Dispose）与"已释放返回 null"的语义未写入接口注释；`IFrame.AddRef` 注释"防止图像帧被GC回收"有误导，实际是原生缓冲引用计数。
4. `HikFrameWrapper.Stride = ImageSize/Height` 对含行填充（padding）的格式可能不准，建议直接取 SDK 行跨度（如有）。
5. `HikCamera.SetBufferCount` 读取 `this.device` 无锁（有 catch 兜底，竞态下返回失败结果，可接受）。
6. `HikCamera.Dispose` 中 `StopGrabCore` 失败仍继续 `device.Close()`（best-effort，已有注释，依赖 SDK 对活跃缓冲的容错）。

## 四、结论

- 帧生命周期主线（回调内 Clone → 归还 SDK 缓冲 → 独立克隆发布 → 订阅者消费/淘汰/取消释放）设计正确，发布方初始引用、DropOldest 淘汰释放、Unsubscribe/Dispose 排空等路径均无遗漏。
- 相机生命周期主线（解绑回调 → StopGrab → 等待在途回调 → Close）正确，失败回滚（RestoreCallbackSubscription）考虑周到。
- 需要处理的是 H1（真实泄漏+静默失效）、H2（泄漏兜底缺失）、H3（并发窗口），以及 M1~M3 的长期运行健壮性问题。
