## 纪律总览

这 8 条是 2026-10-06 审查后确立的**新增厂商必须遵守**的并发纪律。海康完整落地；IRayple 只落地了一部分（生命周期路径经 `operationGate`、回调排空、同句柄只 attach 一次、`LastError`），**参数/命令路径仍在 `operationGate` 之外，生命周期仍是 `isOpen`/`isGrabbing`/`disposed` 多个 `int` 标志位**（第 1、2、3 条未完全落地），见 [[厂商适配/IRayple现状]]。每条纪律背后都有一个已经真实发生过的缺陷，所以它们不是风格偏好而是正确性约束。

| # | 纪律 | 主要载体 |
| --- | --- | --- |
| 1 | 一切原生访问经 `operationGate` | `HikCamera` 的 `SemaphoreSlim operationGate = new(1, 1)` |
| 2 | 生命周期用单一状态枚举 | `private enum CameraState` + `int state`（`Volatile` 读写） |
| 3 | 失败路径必须回滚 | `RestoreAfterFailedClose` / `StopGrabCore` |
| 4 | 门面按 `cameraKey` 串行 | `CameraService.GetKeyLock(cameraKey)` |
| 5 | `CameraStream.operationLock` 只保护订阅者注册表 | `CameraStream.operationLock` |
| 6 | SDK 回调线程只读状态 + 归还缓冲 | `ProcessFrameCallBack` |
| 7 | 关闭前排空在途回调（上限 5s） | `WaitForCallbacks` + `CallbackDrainTimeout` |
| 8 | SDK 全局生命周期引用计数 | `HikCameraSdkSystem` 静态计数 + 全局锁 |
| 9 | 设备异常回调（SDK 线程）不进门，只在 `stateLock` 内迁移 `Lost`，事件异步派发（1.2.0） | `HikCamera.OnDeviceException` / `RaiseDisconnected` |

## 一切原生访问经 operationGate

海康把互斥、异常翻译、诊断三件事收敛到三个守卫：

| 守卫 | 签名 | 职责 |
| --- | --- | --- |
| `ExecuteGuarded` | `CameraResult ExecuteGuarded(Func<CameraResult> action)` | 互斥 + `MvException` → `CameraResult.Fail(me.ErrorCode, me.Message)`、其它异常 → `Fail(-1, e.Message)` + 写 `LastError` |
| `TryExecuteGuarded<T>` | `bool TryExecuteGuarded<T>(Func<(bool Ok, T Value)> action, out T value)` | 取参路径：同样的门与异常收敛，失败返回 `false` |
| `ExecuteDispose` | `void ExecuteDispose(Action action)` | 释放路径：同样的门，不返回结果、不外泄异常 |

`Connect` / `Close` / `StartGrab` / `StopGrab` / `Dispose` 全部是这几个守卫的一行 lambda；参数与命令路径走 `ExecuteGuarded` / `TryExecuteGuarded`。

**唯一例外**：SDK 采集回调线程 `ProcessFrameCallBack` 不经 `operationGate`（否则回调与 `Close` 会互锁死），它只在 `stateLock` 内读状态并归还 SDK 缓冲。

> [!danger] 历史缺陷：参数与命令路径（`SetParam`×4、`SetEnumParam`、`ExecuteCommand`、`TryGetParam`、`TryGetEnumParam`）曾完全在互斥之外。与 `Dispose` 并发时设备字段已被清空，直接抛 `NullReferenceException` 穿透到调用方。凡新增写操作必须并入守卫，没有例外。

## 单一状态枚举

```csharp
private enum CameraState
{
    Closed = 0,    // 已创建未打开
    Open = 1,      // 已打开未取流
    Grabbing = 2,  // 正在取流，帧回调发布
    Closing = 3,   // 正在关闭：已停止发布帧，等待在途回调排空
    Disposed = 4,  // 已释放（终态）
    Lost = 5       // 设备已掉线（1.2.0）：SDK 线程迁移进入，由 Close/Connect 释放句柄
}
```

字段是单个 `int state`（`= (int)CameraState.Closed`），用 `Volatile.Read` / `Volatile.Write` 读写，供回调线程与操作线程共享：

- `IsGrabbing` ⇔ `state == Grabbing`。
- `IsConnected`（公开属性）⇔ `state ∈ {Open, Grabbing, Closing}`（含 `Closing`：此时设备尚未释放）。**1.1.2 起是纯状态读取**：不读 `device`、不做原生调用，可在任意线程调用。此前它在门外读 `device` 并调用原生 `IsConnected`，与 `DisposeCore` 置空并发会 NRE。
- 原生层面的连接检查只能在门内经 `IsDeviceReady()`：状态 Open/Grabbing，且对 `device` 做一次局部快照后取 `device.IsConnected`。`CheckReady`、`CurrentParameters`、`SetEnumParam`、`ExecuteCommand`、`TryGetParam`、`TryGetEnumParam`、`StartGrabCore` 都使用它。
- 帧回调发布判定**只看状态**：`Open` 或 `Grabbing` 才发布。

> [!danger] 历史缺陷：曾用 `isOpen` / `isGrabbing` / `closing` / `callbacksEnabled` / `disposed` 五个并行布尔标志位。`Close` 的 catch 分支忘记回滚 → `closing` 永久为 `true` → 帧回调判定为"不发布" → 相机仍然 `IsConnected` 却**一帧不发**，静默丢帧且无任何报错。单枚举从结构上排除了"标志位组合非法"。

## 失败路径必须回滚

`CloseCore` 的流程（1.2.0）：`Lost` 则直接 `TearDownLostDevice()`；否则经 `TryMoveState(Open/Grabbing → Closing)` 进入 `Closing`（若 SDK 线程已先迁为 `Lost`，同样转入释放路径）→ 解绑 `FrameGrabedEvent` → `StopGrabCore` → `WaitForCallbacks` → 关设备 → 成功后解绑 `DeviceExceptionEvent`，再置 `Closed` 并清 `LastError`（设备异常回调在关闭期间保持绑定，见下）。1.2.0 验收修正后，状态为 `Closed`（已关闭或从未打开过）时 `Close` 直接返回成功，不做原生调用、不依赖 `device` 是否为 null（幂等）；`Camera not initialized` 仅作防御保留。**任何一步失败都走同一个回滚点** `RestoreAfterFailedClose(previousState, currentGrabber, currentDevice, failure)`：判定在 `stateLock` 内完成——若已为 `Lost` 则改走 `TearDownLostDevice()` 并返回其结果（不回滚到 `previousState`）；否则在同一临界区内恢复 `previousState`，再 `RestoreEventSubscriptions(currentGrabber, currentDevice)`（1.2.0 起同时恢复设备异常回调，原名 `RestoreCallbackSubscription`）——后者用"先 `-=` 再 `+=`"的方式重新绑定回调订阅，使调用方还能重试关闭或继续取流。

`StopGrabCore(currentGrabber, wasGrabbing)` 只在 native `StopGrabbing()` 返回 `MV_OK` 后才清取流状态（`Grabbing → Open`，且仅当当前状态确为 `Grabbing`，避免在 `Close` 期间把状态改回 `Open` 让回调又开始发布）。native 失败时**保留**取流状态，防止向上一层伪装成"已停止"。

## 门面按 cameraKey 串行

`CameraService` 用 `ConcurrentDictionary<string, object> cameraKeyLocks` + `GetKeyLock(cameraKey)`。持锁的写操作只有五个：`OpenCamera`、`Close`、`StartGrab`、`StopGrab`、`SetTrigger`。

锁对象**按 key 只增不减**：key 数量量级 ≈ 相机数（小而稳定），可接受；按引用计数删除会在 `Close`/`OpenCamera` 竞态窗口重开两个锁对象，得不偿失。

> [!danger] 历史缺陷：`Close` 曾是唯一不持锁的写操作，会在 `OpenCamera` 的 `Connect()` 中途把实例从注册表摘出并释放 → use-after-free。**新增写操作必须并入 `GetKeyLock`**，否则同一类竞态会重现。注意 `SetParam` / `ExecuteCommand` / `TryGetParam` 这类读参与写参路径**有意不持锁**——它们在厂商相机内部由 `operationGate` 保护，门面持锁只会增加死锁面。

## CameraStream 的锁边界

`CameraStream.operationLock` **只保护订阅者注册表**（`subscribers` 字典与 `disposed` 标记）。以下操作一律在锁外：`frame.AddRef()` 与发布方初始引用的释放、`subscriber.TryWrite(frame)`、背压淘汰时 5MB 帧的释放、用户 `whenException` 回调。`Publish` 路径上锁内只做一件事：取订阅者快照（`subscribers.Values.ToArray()`）；`Subscribe`/`Unsubscribe`/`Dispose` 在锁内读写订阅者字典与 `disposed` 标记，其余清理仍在锁外。

> [!warning] 历史缺陷：曾在锁内做这些重活，导致订阅/退订被慢速释放阻塞；更危险的是用户 `whenException` 回调可能在锁内被调用——若用户在该回调里从另一线程回调进同一个流并等待，即死锁。

死订阅清理 `RemoveDeadSubscriber` 是例外：它需要在锁内做"仅当字典中仍是同一实例才移除"的判定，但 `self.Dispose()` 放在锁外。

## SDK 回调线程纪律

`ProcessFrameCallBack(object sender, FrameGrabbedEventArgs e)` 运行在 SDK 采集线程上：

1. `frameOut == null` 直接返回。
2. `stateLock` 内：`inFlightCallbacks++`；读状态判定 `shouldPublish`；捕获 `fallbackGrabber = this.streamGrabber`。
3. `try`：`shouldPublish` 时 `frameOut.Clone()`，克隆帧包成 `HikFrameWrapper` 后 `stream.Publish(frame)` 并把局部变量置 `null`（所有权已移交）。`Clone` 返回非空但类型不符时必须 `Dispose` 掉它，否则克隆帧泄漏。
4. `catch`：异常不得外泄（会中断采集），就地 `frame?.Dispose()`。
5. `finally`：**无论相机是否正在 Dispose**，都用 `callbackGrabber ?? fallbackGrabber` 归还 SDK 缓冲（`(grabber)?.FreeImageBuffer(frameOut)`）；归还失败记 `LastError`。最内层 `finally` 在 `stateLock` 内 `inFlightCallbacks--`，归零时 `Monitor.PulseAll(stateLock)`。

回调内**不做重活**：除了 Clone 与 Publish，不做参数访问、不做设备控制。

## 设备异常回调（掉线）纪律（1.2.0）

`OnDeviceException(object sender, DeviceExceptionArgs e)` 与帧回调一样运行在 **SDK 线程**上，因此：

1. **绝不进入 `operationGate`**。门内的 `device.Close()` 可能正在等待本回调返回，若回调再取门即死锁。这是计划 B 的关键约束，回归守卫为 `HikCameraStateTests.DeviceException_WhileDisposeWaitsForInFlightCallback_DoesNotDeadlock`（`Dispose` 持门并等待在途回调时，掉线回调必须在 2 秒内返回）。
2. `stateLock` 内只做一件事：`Open`/`Grabbing` 时条件迁移为 `Lost` 并写入 `LastError`（`Device disconnected (MsgType=…)`）；`Closing` 时同样迁为 `Lost` 并写入 `LastError`，但不派发事件（由关闭路径收尾）；其它状态（`Closed`/`Disposed`/已 `Lost`）忽略，保证同一次连接最多通知一次。
3. 锁外 `ThreadPool.QueueUserWorkItem` 派发 `Disconnected`，逐个调用订阅者并**吞掉其异常**（线程池上未观察的异常会终止进程）；整个回调 `try/catch`，异常不得外泄到 SDK。
4. 所有门内状态写入（`SetState`、`TryMoveState`）都在 `stateLock` 内完成，与第 2 点的迁移互斥；诊断清空与迁移处于同一临界区，不会覆盖掉线原因。
5. `Closing` 期间的掉线只迁为 `Lost`（不派发）；关闭失败回滚时发现 `Lost` 则改走释放路径，不会留下"假连接"（验收修正，见 CHANGELOG 1.2.0 偏离项 5）。

## 关闭前排空在途回调

`private static readonly TimeSpan CallbackDrainTimeout = TimeSpan.FromSeconds(5);`。`WaitForCallbacks()` 在 `stateLock` 上以 `Monitor.Wait(stateLock, remaining)` 等待 `inFlightCallbacks` 归零，`deadline = DateTime.UtcNow + CallbackDrainTimeout`。超时则写 `LastError`（`"Timed out waiting for N in-flight frame callback(s) to drain."`）并 `break`——**继续关闭**，避免 `Close`/`Dispose` 永久阻塞。调用点有两处：`CloseCore` 中在停流之后、关设备之前；`DisposeCore` 中在停流之后、`SafeClose` 之前（先置终态 `Disposed` 让回调立即停止发布）。

## SDK 全局生命周期引用计数

`HikCameraSdkSystem` 用静态 `initRefCount` + 静态 `refCountLock` + 每实例 `instanceLock`/`initialized` 管理全局 SDK：

- `Initialize()` 已释放则返回；`instanceLock` 内若已 `initialized` 则返回——**按实例幂等**；`++initRefCount == 1` 时才真正调用 `SdkInitializeAction()`。**1.1.2 起检查原生返回码**：返回值非 `MV_OK` 时回退计数并抛 `InvalidOperationException("…error code 0x…")`，`initialized` 保持 false；抛异常同样先回退计数再重抛（保证引用计数与现实一致）。
- `Release()`：`instanceLock` 内若未 `initialized` 直接返回——**未 Initialize 的实例 Release 不削减他人引用**；`--initRefCount` 到 0 时才 `SdkFinalizeAction()`。1.1.2 起 Finalize 返回非 `MV_OK` 只 `Trace.TraceWarning`，不抛。**计数先于 Finalize 递减，`initialized = false` 放在 `finally` 中**：Finalize 抛异常时本实例已不持有引用，第二次 `Release` 不会再次递减。`Dispose()` 置 `disposed` 后调用 `Release()`。
- 计数转移**全部在 `refCountLock` 内**完成（锁内用普通 `++/--`），封死"并发 Initialize 与 Finalize 交叉"的窗口。

测试通过 `internal static Func<int> SdkInitializeAction` / `SdkFinalizeAction` seam 替换真实 SDK 调用（经 `InternalsVisibleTo` 供无硬件单测使用）。seam 的返回值即 SDK 错误码，桩必须返回 `MV_OK`（0），否则会被当作初始化失败。多厂商组合场景用 `CompositeCameraSdkSystem` 把多个 `ICameraSdkSystem` 合成一个。

## 门与状态的关系

```mermaid
flowchart TD
    A[调用方: Connect/Close/StartGrab/StopGrab/SetParam/TryGetParam/Dispose] --> B{operationGate<br/>SemaphoreSlim(1,1)}
    B -->|获取| C[执行 native 调用]
    C -->|成功| D{更新单一状态枚举<br/>CameraState}
    C -->|MvException / Exception| E[SetLastError<br/>翻译为 CameraResult 或 false]
    E --> F[返回 CameraResult.Fail / false]
    D --> G[ExecuteGuarded finally: Release]
    F --> G
    H[SDK 采集回调线程 ProcessFrameCallBack] -.唯一例外:不取门.-> I[stateLock 内: inFlightCallbacks++<br/>判状态决定是否发布]
    I --> J[Clone 一次 -> stream.Publish]
    J --> K[finally: FreeImageBuffer 归还 SDK 缓冲]
    K --> L[stateLock 内: inFlightCallbacks--<br/>归零 PulseAll]
    M[Close/Dispose] --> N[WaitForCallbacks<br/>上限 CallbackDrainTimeout = 5s]
    L --> N
```
