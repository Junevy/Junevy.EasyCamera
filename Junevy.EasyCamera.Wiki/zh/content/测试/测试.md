## 本分类概述

`Junevy.EasyCamera.Tests` 是本仓库唯一的验证载体，MSTest 框架、双目标 `net48;net8.0`、测试宿主固定 `x64`。当前基线（2026-10-09，1.2.0 验收修正后）：**149 个 `[TestMethod]`，net48 与 net8.0 各 149/149 通过**（1.1.1 发布时为 124；1.1.2 批次 A 新增 9 项；1.2.0 掉线批次新增 16 项，含验收修正新增 4 项）。

它有三个别处看不到的特点，构成本分类存在的理由：

1. **无硬件依赖**。厂商 SDK 全部由桩件替代：`Mocks/` 下的替身替换公共层实现，`Vendors/` 两个测试文件里的私有嵌套类替换海康 `MvCameraControl` 的原生接口，`HikCameraSdkSystem.SdkInitializeAction/SdkFinalizeAction` 这两个 internal 测试 seam 替换真实 `SDKSystem.Initialize/Finalize`。因此在没有相机的开发机上测试也能全绿。
2. **显式编译清单**。csproj 设了 `EnableDefaultCompileItems=false` 并逐个列出 `<Compile Include>`。这是 1.1.0 期间"6 个探测测试从未参与编译"事故的直接成因——新增测试文件不手工登记，就是一份永远不会执行、也不报错的代码。
3. **有一类缺陷单元测试天然测不到**。厂商 SDK 托管封装是否真被打进 NuGet 包，本仓库怎么 build/test 都是绿的，只有消费方还原后才崩。`Packaging/PackageContentTests.cs` 因此绕开单元测试，直接解压 nupkg 校验条目。

设计上的并发纪律与引用所有权背景见 [[并发与资源/并发纪律]] 与 [[并发与资源/帧所有权与内存]]；本分类只讲"如何验证这些纪律不回归"。

## 验收纪律

```powershell
dotnet build .\Junevy.EasyCamera.sln -c Release -v:minimal --no-incremental
dotnet test .\Junevy.EasyCamera.Tests\Junevy.EasyCamera.Tests.csproj -c Release --logger "console;verbosity=minimal"
```

两条必须一起做的核对：

| 核对项 | 期望 | 不符时说明 |
| --- | --- | --- |
| 仓库内 `[TestMethod]` 总数（排除 `obj/`） | 133 | 变少＝有测试文件被误删或被移出编译清单 |
| `dotnet test` 实际执行数（每个 TFM） | 各 133 | 变少＝新测试文件未加入 csproj 的 `Compile` 清单 |
| 构建 | 0 错误 0 警告 | 有警告说明有 `NoWarn` 之外的妥协 |

`PackageContentTests` 在找不到 nupkg 时断言为 Inconclusive 而非失败，所以未先做 Release 构建就跑测试不会产生假红，但也**不会**真正校验打包内容——这是"绿灯但没测到"的另一种形态。

> [!danger]
> `EnableDefaultCompileItems=false` 是本工程最反直觉的设置。2026-10-06 的审查发现 `CameraServiceProbeTests.cs` 已在仓库里躺着、CHANGELOG 也写着"6 项探测测试"，但因为没进 `<Compile>` 清单，实际从未编译过一次（当时仓库实有 98 个 `[TestMethod]`，只执行 92 个）。这类缺陷的特征是**完全静默**：不报错、不失败、CI 全绿。所以"仓库内测试总数 == 执行数"是唯一的检测手段，必须每次验收都做。

> [!tip]
> 校验命令（2026-10-08 批次 A 后实测返回 133）：
> ```powershell
> (Get-ChildItem .\Junevy.EasyCamera.Tests -Recurse -Filter *.cs | Where-Object { $_.FullName -notmatch '\\(bin|obj)\\' } | Select-String -Pattern '\[TestMethod\]' | Measure-Object).Count
> ```
> 此前这里写的 `Select-String -Path .\Junevy.EasyCamera.Tests\*\*\*.cs` 是**错的**：测试文件只有两级深（`Tests\Common\X.cs`），三层通配匹配不到任何文件，实测返回 **0**——拿它核对会得出"一个 `[TestMethod]` 都没有"。别用。

## 新增测试的正确姿势

1. 在对应目录建 `.cs` 文件（`Abstractions/`、`Common/`、`Extensions/`、`Vendors/`、`Packaging/`）。
2. **立刻**把相对路径加进 csproj 的 `<Compile Include>` 清单——和第 1 步是同一次提交，不可拆分。
3. 需要新替身时，加进 `Mocks/` 并同样登记；厂商 SDK 桩件写进对应的 `Vendors/*Tests.cs` 私有嵌套类，不新建文件（省掉一次登记）。
4. 跑测试，核对本分类"测试文件清单与数量"表里的总数与执行数同步增长。
5. 若改动的是公共契约或打包规则，同步核对 [[Agent协作/文档同步清单与任务配方]] 里列出的必改文件。

> [!warning]
> 如果这次修的是一个真实缺陷，强烈建议先"移除修复 → 确认对应用例变红 → 恢复修复 → 确认变绿"。仓库里已有两处这样验证过的记录：`CameraService_Close_WaitsForInFlightOpenOnSameKey` / `CameraService_StartGrab_WaitsForInFlightCloseOnSameKey`（移除 per-key 锁修复后立即失败）与 `Package_ShouldContainVendorManagedAssembliesForEveryTargetFramework`（移除打包规则后立即失败）。没有这个动作，无法区分"测试真的在守护"和"测试恰好通过"。
