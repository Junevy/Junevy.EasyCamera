## 运行时位数：必须 x64

`net48` 与 `net8.0` 两个目标下，`Junevy.EasyCamera` 与 `Junevy.EasyCamera.Tests` 都固定了 `PlatformTarget=x64`（海康/华睿 SDK 为 AMD64 专用）。宿主若按 AnyCPU 或 x86 发布，加载厂商程序集时会抛 `BadImageFormatException`。

- 消费方工程：`<PlatformTarget>x64</PlatformTarget>`（或直接发布 x64 目标）。
- 框架宿主（IIS / WinForms / WPF 应用池）同样要确认"启用 32 位应用程序"为关闭。

## 厂商原生运行时必须自行安装

厂商的**原生**驱动 DLL（如 `MvCameraControl.dll`）**不在 NuGet 包内**，由厂商安装程序（MVS 等）部署，并要求其运行时目录在 PATH：

```
...\Common Files\MVS\Runtime\Win64_x64
```

安装程序通常会自动配置 PATH，但精简镜像、容器化部署、CI 机器上常常缺失。缺失时的表现是 `Initialize` 抛 `DllNotFoundException`，或托管封装明明在位却枚举不到任何设备——成因与"托管封装缺失"不同，必须分清。

## 厂商托管封装随包分发

自 **1.1.1** 起，厂商**托管**封装（`MvCameraControl.Net.dll`、`MVSDK_Net.dll`）已打进 NuGet 包的 `lib/net48` 与 `lib/net8.0`，消费方只需正常 `Install-Package` / `PackageReference`，**不需要**手工拷贝任何 DLL。

> [!danger]
> 不要手工把厂商 DLL 拷到 exe 旁边——这对 .NET Core **无效**：程序集解析走 `deps.json` 的 TPA 列表，默认加载器不探测 exe 目录。这曾导致"拷了还是崩"的误判，把排查方向完全带偏。验证方式是看构建输出目录里有没有这两份 DLL（由 NuGet 资产复制而来），而不是看你有没有手动复制。

`≤1.1.0` 的包**没有**打包这两份 DLL，消费方还原后 `ICameraSdkSystem.Initialize()` 抛 `AggregateException`（内含 `type initializer for 'HikCameraSdkSystem' threw an exception`），`EnumerateCameras()` 抛 `FileNotFoundException('MvCameraControl.Net, Version=4.5.0.2')`，未捕获即崩溃。

> [!warning]
> 刻意没有采用"依赖 nuget.org 上的 `MvCameraControl.Net`"方案：那里只有第三方未验证转包（1.1.0 / 4.4.1.x / 4.8.0.3），与本仓库 pin 的 **4.5.0.2** 对不上，依赖它等于引入供应链风险。

## 升级必须清理 NuGet 缓存

NuGet 按 `id + version` 缓存，**同版本重发不会被消费方采用**（1.1.1 修复过程中即被该缓存误导过一次）。升级步骤：

1. 包版本升到 1.1.1 或更高。
2. 清理旧版本缓存后重新还原：
   - 删 `%USERPROFILE%\.nuget\packages\junevy.easycamera*`，或
   - 还原加 `--force`；若本机把缓存放在自定义 `RestorePackagesPath`（例如 `D:\Documents\Nuget\RemoteCache`），须删**该目录下**的 `junevy.easycamera*` 条目。
3. 确认输出目录出现 `MvCameraControl.Net.dll` 与 `MVSDK_Net.dll`；没有就说明拿到的仍是旧包。
4. 再确认厂商原生运行时（MVS）已安装且 `...\Common Files\MVS\Runtime\Win64_x64` 在 PATH——这与托管封装是两回事。

> [!tip]
> 本地开发可直接消费仓库构建产出的 nupkg（`GeneratePackageOnBuild=true`，产物在 `Junevy.EasyCamera/bin/<Config>/` 与 `Junevy.EasyCamera.Core/bin/<Config>/` 下，`<Config>` 为 `Debug`/`Release`，**不是**按 TFM 分目录）。主包依赖同版本的 `Junevy.EasyCamera.Core`，本地 feed 里两个 nupkg 都要有。验收时应验证"仅引用真实产出的 1.1.1 nupkg、零手工拷贝 DLL"的端到端路径——1.1.1 的验收就是这么做的（net8.0 与 net48 消费方均 `Initialize OK` + `EnumerateCameras OK`）。

## 打包链路的可复现性守卫

`Tests/Packaging/PackageContentTests.cs` 是打包内容的回归守卫：定位仓库根、取最新 nupkg，断言两个 TFM 下均含 `MvCameraControl.Net.dll` 与 `MVSDK_Net.dll`；找不到产物时断言为 Inconclusive，不产生假失败。已验证**移除打包规则后该测试立即失败**。

这类缺陷单元测试天然测不到（本仓库全绿、消费方必崩），因此直接校验打包产物。任何对 `PackagePath` 的"顺手简化"都必须先确认该测试仍然通过。

## 排错对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `FileNotFoundException: Could not load file or assembly 'MvCameraControl.Net'` | 包内缺厂商托管封装（≤1.1.0 的已知缺陷），或缓存未清 | 升级到 1.1.1+，清理旧版本 NuGet 缓存 |
| `AggregateException: The type initializer for 'HikCameraSdkSystem' threw an exception` | 同上，`Initialize` 路径上的表现 | 同上 |
| `BadImageFormatException` | 宿主非 x64 | 改 `PlatformTarget=x64`；检查应用池"启用 32 位应用程序" |
| 手工拷了厂商 DLL 到 exe 旁边仍然崩 | 对 .NET Core 无效（不走 deps.json 探测） | 必须通过 NuGet 依赖分发，删除手工拷贝的做法 |
| `Initialize` 抛 `DllNotFoundException`，或枚举不到设备但托管封装已在 | 厂商原生运行时未安装或不在 PATH | 安装 MVS 运行时，确认 `...\Common Files\MVS\Runtime\Win64_x64` 在 PATH |
| 枚举结果为空 | 相机未上电 / 网段不通 / GigE 带宽被防火墙拦下 | 检查网线与网卡配置；库会 `Trace.TraceWarning` 输出厂商错误码（`HikCameraProvider.Enumerate failed with code ...`） |
| 收不到帧 | 未 `StartGrab`；`cameraKey` 拼错；订阅因 handler 异常且无 `whenException` 被自动摘除；触发模式下无触发信号 | 按此四项逐个排除；帧链路的判定规则见 [[架构设计/帧数据流与生命周期]] |
